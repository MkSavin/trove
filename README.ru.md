# trove

**Архив аудитов, планов и спецификаций в обычном Markdown — с одной проверкой.**

Правила живут в конфиге, а не в прозе. Markdown остаётся источником правды: люди читают файлы как есть, а инструмент их проверяет, ищет по ним и собирает отчёты.

```console
$ trove check
audits/AUDIT_WEB_1.md
  12  error  status line says closed, header open                 status-line
  21  error  7 cells against 6 in the header; a | inside a cell?  ledger-row-shape

✖ 2 errors, 0 warnings, 1 info · 20 documents · 5 ledgers · 16 open items
```

## Зачем

- **Один регламент.** Типы документов, статусы, колонки реестра и жизненный цикл — данные в `trove.yaml`. Новый тип, колонка или отчёт — правка конфига, а не кода.
- **Правда — в файлах.** Каждый документ — обычный Markdown в git. Всё, что хранит инструмент (индекс, сгенерированные отчёты), пересобирается из файлов.
- **Срезы, а не файлы.** `query` и `show` возвращают один пункт или один раздел: ни человеку, ни ассистенту не нужно открывать бэклог на 200 КБ ради одной находки.

## Быстрый старт

Нужен git. Возьмите однофайловый бинарник из [Releases](https://github.com/MkSavin/trove/releases) и положите в `PATH` как `trove` или установите из исходников через [Bun](https://bun.sh) ≥ 1.4.

```sh
bun add -g github:MkSavin/trove    # или бинарник из Releases
cd ~/git/app                       # ваш проект
trove init --lang ru               # ../app-trove: зелёное хранилище, связанное и закоммиченное; в дереве проекта ничего
trove doc new audit "веб-клиент" --scope web/
trove item add AUDIT_WEB_CLIENT_1 priority=P1 owner=web "what=Отправка без сети теряется"
trove item close WEBCLIENT1-1 --commit 3f2a9c1
```

Коллега запускает `trove clone <адрес-хранилища>` в своём клоне проекта: хранилище встаёт рядом и привязывается, тоже без следов в дереве проекта. С `trove init --share` проект вместо этого коммитит `.trove.yaml`, и простой `trove clone` подтягивает все хранилища из него. Уже ведёте такой архив руками? `trove migrate ../notes ../app-trove` соберёт из него хранилище: история git и незакоммиченная работа переедут, конфиг подгоняется под документы, а сам архив только читается.

## Команды

**Настройка**

| команда | что делает |
| ------- | ---------- |
| `trove init [--path] [--remote] [--lang en\|ru] [--share] [--no-git]` | Создаёт хранилище для текущего проекта: папки, конфиг, заметки, отчёты, git с проверкой перед коммитом, привязку в `.git/trove.yaml` (с `--share` — закоммиченный `.trove.yaml`), запись в `~/.trove/registry.yaml`. Задаёт не больше трёх вопросов, у каждого есть ответ по умолчанию; `--yes` принимает их все. |
| `trove clone [<store-url>] [--path] [--name] [--share]` | Клонирует хранилище по адресу рядом с проектом и привязывает его приватно; без адреса — клонирует и регистрирует хранилища из указателя проекта. |
| `trove resync [--continue] [--seal]` | Переносит то, что изменилось в исходном архиве после миграции или прошлого `resync`, закоммиченное и нет, трёхсторонним слиянием: правки самого хранилища остаются, документ, который хранилище уже убрало в архив, получает изменение там, документ, который исходный архив перенёс в свою папку архива, переносится и в хранилище, конфликты ждут `--continue`. Исходный архив только читается, кроме `--seal`. |
| `trove migrate <archive> <store> [--drop FILE] [--project DIR [--link]]` | Собирает хранилище из существующего архива: клон с историей, незакоммиченная работа отдельным коммитом, конфиг под документы (язык, лишние типы, статусы и пишутся ли они ключами, поля, колонки реестра по типам, строка статуса только там, где она есть в документах, какие статусы лежат в архиве, порядок групп старого бэклога), пересобранные отчёты, подсчёт документов и пунктов до и после. Исходный архив только читается, его remote не переносится. `--project` привязывает хранилище к проекту приватно, `--link` — через закоммиченный `.trove.yaml`. |
| `trove store add <name> --scope <glob>` | Ещё одно хранилище — для команды со своим доступом; команды из папок под `--scope` идут в него. |
| `trove remote add <url>` | Подключает локальное хранилище к удалённому репозиторию, переключает `sync` на `push` и отправляет историю. |
| `trove client add <claude\|cursor\|codex> [--local]` | Регистрирует MCP-сервер и скиллы для ассистента в этом проекте; `--local` оставляет их на этой машине, вне проекта (Claude Code). |
| `trove doctor` · `trove forget` | Показывает проект, его хранилища и их состояние; внутри хранилища — его и проект, к которому оно привязано в реестре · убирает проект из реестра этой машины. |

**Чтение**

| команда | что делает |
| ------- | ---------- |
| `trove check [file] [--all] [--json] [--verify]` | Запускает все правила; при ошибках выходит с кодом 1. `--all` дополнительно перечисляет все документы. `--verify` ещё и запускает `verify-cmd` всех документов в работе и выходит с кодом 1, если какая-то не прошла (см. повторяемые проверки ниже). |
| `trove query items status=open owner=web [--columns a,b]` | Фильтрует пункты или документы по любому полю (см. фильтры ниже). У пунктов — колонки реестров, из которых они взяты, `id` первым; `--columns` выбирает другие. |
| `trove summary show [kind] [filters]` | Сводка на экран, без записи: настроенный вид или подсчёты, открытые пункты по документам и документы в работе под заданными фильтрами. |
| `trove show WEB1-4` | Печатает раздел одного пункта, в том числе закрытого; если id нет ни в одном реестре — все разделы с ним в заголовке, архив включительно. Принимает и `DOC#заголовок` или имя документа — тогда его оглавление. |
| `trove prompt PROMPT_X [--copy]` | Печатает текст задания промпта или копирует его; кириллица не ломается и в Windows. |
| `trove report [name...]` · `trove rules` | Пересобирает сгенерированные отчёты и все живые сгенерированные блоки · список правил с действующим уровнем. |
| `trove refresh [doc...]` | Перезаполняет сгенерированные блоки названных документов, в том числе сводки после её даты, или всех живых; после ручной правки внутри блока. |
| `trove links [--dead]` | Относительные ссылки на документы и код; код проверяется в `roots`, которые есть на этой машине: в рабочей копии или, с `{ path, ref: origin/main }`, на этом коммите, какая бы ветка ни была открыта; файлы, которые git там игнорирует, например установленные пакеты, читаются из рабочей копии. `--dead` заканчивается строкой `N dead of M links`. |
| `trove export items [filters] --format csv\|json [--columns a,b]` | Строки для CRM или таблицы; CSV по RFC 4180. |

**Правка.** Каждая правка меняет только свои строки, сохраняет CRLF, сначала проверяется в памяти и не записывается, если добавляет ошибку. Сгенерированные отчёты пересобираются тем же шагом; `--dry-run` вместо записи печатает построчный diff.

| команда | что делает |
| ------- | ---------- |
| `trove doc new <type> <topic> [--scope] [--field k=v]` | Документ по шаблону типа: папка, префикс, следующий номер серии, slug. Имя — первые восемь слов темы заглавными, кириллица транслитерируется (`чего не хватает` → `CHEGO_NE_KHVATAET`); для других алфавитов нужен `--name`. |
| `trove doc archive <doc> [--status closed]` | Переносит в зеркальную папку архива, ставит статус, чинит относительные ссылки с обеих сторон. Статус, с которым `lifecycle` отправляет тип в архив (например, закрытый план), сохраняется; `--status` ставит его тем же шагом. |
| `trove doc retype <doc> <type>` | Превращает документ в другой тип, например исследование, ставшее планом работ: папка, префикс, статус, заголовок, ссылки и упоминания следуют за ним. |
| `trove summary new <kind> [filters] [--from latest\|DOC] [--keep] [--name]` | Датированная сводка этого вида: сгенерированные блоки заполнены, места `<!-- write: … -->` оставлены для анализа. `--from latest` сохраняет структуру шаблона и заполняет каждое место write текстом под той же строкой `<!-- write: … -->` в последней сводке этого вида, а если её нет — тем, что стоит после того же заголовка или блока. Сводки этого вида, что ещё в работе, уезжают в архив, каждая называет преемника в `superseded_by`; `--keep` их оставляет. |
| `trove doc checked <doc>` · `trove doc set <doc> <field> <value>` | Сверено сегодня · любое поле шапки; `status` заодно обновляет строку статуса. |
| `trove item add <doc> column=value...` | Строка реестра со следующим свободным id и заготовкой раздела (`ledger.heading`, `ledger.stub`). Номера закрытых пунктов не переиспользуются. |
| `trove item close <id> [--as OUTCOME] [--commit SHA] [--archive]` | Убирает строку и перечисляет другие упоминания. Тип с `closeInto` переносит строку и раздел в свой документ закрытых пунктов; у остальных раздел помечается закрытым на месте. `--as` — исход (`fixed`, `dropped`, `moved`); `--archive` — если это был последний открытый пункт. |
| `trove item defer <id>` | Ячейку статуса и пометку раздела — в «отложено». |
| `trove item move <id> <doc> [--archive]` | Переносит пункт с разделом в другой реестр под следующим id там; колонки, которых нет у цели, перечисляются. Если у источника есть `closeInto` и исход `moved`, в его реестре закрытых остаётся строка с новым id. |
| `trove links [file] --fix` | Мёртвые ссылки на код ведут на последнюю версию файла: родителя удалившего коммита или, если в истории ref корня файла не было, последний коммит другой ветки, где он есть. Постоянная ссылка, если `origin` на GitHub или GitLab (SSH-алиас раскрывается через `ssh -G`) и коммит там есть, иначе пометка `*(deleted in abc1234)*` или `*(at abc1234)*` после ссылки, которую `dead-link` проверяет на этом коммите. Ссылки, которых нет ни в одной ветке, остаются и перечисляются. |
| `trove sync [-m TEXT]` | Коммитит ручные правки вместе с пересобранными отчётами и отправляет по режиму. Не работает, пока `check` красный. |

**Фильтры** одинаковы в `query`, `summary`, `export`, конфигах отчётов, сгенерированных блоках и инструментах MCP: `field=value` совпадает с сырым текстом или ключом словаря (`status=open` и `status=открыто` — одно и то же), `~text` — подстрока, `*` и `**` — glob, `!` в начале исключает. Пункты фильтруются и по полям своего документа: `owner=web path=!audits/mobile/**` — всё для веб-команды вне мобильных аудитов. Повторите поле или перечислите через запятую, чтобы задать варианты. Закрытые пункты не попадают в выборку, пока фильтр не назовёт `state` (`state=closed`, `state=open,closed`).

**Дрейф.** `drift=true` находит пункты, которые, возможно, уже исправлены: код, на который они указывают, изменился в своём корне после даты `checked` документа — на `ref` корня, а без него на `HEAD`. Пункт указывает на код Markdown-ссылками в своей строке реестра и в собственном разделе, а также именами файлов во встроенном коде там же, например `` `send.ts:41` `` или `` `composer/send.ts` ``; голое имя засчитывается, только когда им заканчивается ровно один файл под git в корнях кода. Ссылка, которая называет строки (`#L41-L63`, `:41-63`), дрейфует, только когда изменились эти строки: они читаются по последнему коммиту не позже `checked`, так что строки, которые лишь сдвинулись, не считаются. Ссылка без строк дрейфует от любого изменения файла или папки. `drift=false` значит, что каждая ссылка проверена и не изменилась; `drift=unknown` — что проверить удалось не всё: пункт не указывает на код, корня нет на этой машине, `checked` не дата или `ref` корня здесь неизвестен. Колонка `drift` в сгенерированном блоке называет изменённые файлы и строки, `—` — без изменений, `?` — неизвестно. Дрейф не видит исправление в коде, на который пункт не указывает, в строках, отличных от названных, за закреплёнными ссылками (`*(at …)*`, `*(deleted in …)*`) или ещё не закоммиченное. Это один `git log` на корень и ещё один `git diff` на корень и дату `checked` для изменённых файлов, на которые ссылаются по строкам; запускается, только когда запрос, блок или отчёт называет `drift`.

**Ожидание.** Пункт (колонка реестра `blocked_by`) или документ (поле шапки `blocked_by`) называет id или документы, которых ждёт; `waiting=true` держится, пока хоть один из них открыт или в работе, — так блок отделяет «можно сейчас» от «ждёт». Отсрочка называет в `until`, что её снимает; когда всё это сделано, об этом скажет `deferral-lifted`. У документов есть ещё поле `owner` и вычисляемое `note` — текст строки статуса после слова статуса, для колонки или подстановки в `format`.

Команды находят хранилище от текущей папки: внутри хранилища, затем через указатель проекта, `.trove.yaml` или `.git/trove.yaml` (по `scope`, если их несколько), затем через реестр, затем — хранилище рядом с проектом, чьи `roots` его называют. `--store <name|dir>` или `$TROVE_STORE` задают его явно.

**Синхронизация.** `sync:` в `trove.yaml` решает, что происходит после правки: `off` не трогает git, `commit` делает один коммит на операцию (`docs: close WEB1-3`), `push` ещё и отправляет. Если удалённая ветка ушла вперёд, trove делает rebase; конфликты в сгенерированных отчётах берут удалённую копию и пересобираются, конфликт в документе, написанном руками, останавливает работу с именем файла, ничего не отправив. Пока `check` красный, ничего не коммитится, force push не делается никогда, а хранилище внутри другого репозитория в него не коммитит.

**Переезд архива.** Хранилище после миграции продолжает git-историю архива, поэтому `migrate` не задаёт remote: отправка хранилища в `origin` архива превратила бы тот репозиторий в хранилище для всех, кто ещё пишет в архив по-старому. Вместо этого он печатает remote архива, готовую команду `trove remote add <url>` и сколько коммитов архива на этом remote ещё нет; дайте хранилищу собственный репозиторий или берите старый только после запечатывания. Пока в архиве ещё работают, `trove resync` держит хранилище в согласии с ним, а `trove doctor` предупреждает, если архив изменился после последнего `resync`. Когда переезд закончен, `trove resync --seal` переносит последние изменения, затем пишет в архив `MOVED.md`, ставит первой строкой его `AGENTS.md` (создав файл, если его нет), где теперь хранилище и что в архив писать нельзя, и коммитит оба файла там, если это git-репозиторий. Это единственная команда, которая пишет в архив.

## MCP

`trove mcp` отдаёт те же операции ассистенту по stdio — для хранилищ папки, в которой запущен. Двенадцать инструментов, каждый покрывает семейство операций через дискриминатор, поэтому список инструментов дёшев в любой сессии:

| инструмент | что делает |
| ---------- | ---------- |
| `trove_query` · `trove_show` | строки пунктов или документов по фильтрам · раздел одного пункта, `DOC#заголовок` или оглавление |
| `trove_summary` | сводка настроенного вида или собранная по фильтрам, без записи |
| `trove_check` · `trove_regulation` · `trove_prompt` | диагностика · как устроено это хранилище, по его конфигу · текст задания промпта |
| `trove_create` · `trove_update` · `trove_transition` | новый документ по шаблону · поле шапки · перенос в архив с починкой ссылок |
| `trove_item` | `add`, `close`, `defer`, `move` для пунктов реестра |
| `trove_report` · `trove_sync` | пересборка сгенерированных документов · коммит ручных правок и отправка |

Правки возвращают затронутые файлы с построчным diff; `dryRun: true` возвращает diff без записи, а отклонённая правка перечисляет ошибки, которые она добавила бы. Ресурсы: `trove://regulation/{topic}`, `trove://config`, `trove://template/{type}`.

### Ассистенты

| клиент | как подключить |
| ------ | -------------- |
| Claude Code | `/plugin marketplace add MkSavin/trove`, затем `/plugin install trove@trove-marketplace`: MCP-сервер, оба скилла и хуки, которые запускают `check` на каждом изменённом документе хранилища и `sync` в конце сессии. |
| Cursor | `trove client add cursor`: `.cursor/mcp.json` и `.cursor/skills/`. |
| Codex | `trove client add codex`: `[mcp_servers.trove]` в `.codex/config.toml` и `.agents/skills/`. |
| любой | `trove client add claude` пишет `.mcp.json` и `.claude/skills/` без плагина; `trove init --client <name>` делает это при создании. |
| только эта машина | `trove client add claude --local` ничего не пишет в проект: MCP-сервер попадает в запись этого проекта в `~/.claude.json` (как `claude mcp add --scope local`), скиллы — в `~/.claude/skills/`, оба — в `$CLAUDE_CONFIG_DIR`, если он задан. Cursor и Codex хранят MCP-серверы только в проекте или для всех проектов сразу, поэтому `--local` для них отклоняется. |

Скиллы `trove-store` и `trove-migrate` лежат в одном месте, [`plugin/skills`](plugin/skills), и встраиваются в бинарник, поэтому все клиенты получают один и тот же текст.

## Понятия

**Проект и хранилище.** Проект — ваш репозиторий с кодом. Хранилище — отдельный git-репозиторий его документов, по умолчанию рядом. Доступ к хранилищу — это доступ к его репозиторию.

По умолчанию trove не оставляет следов в дереве проекта: привязка лежит в `.git/trove.yaml`, который git не показывает и не коммитит, и в `~/.trove/registry.yaml`; даже без них находится хранилище рядом с проектом, чьи `roots` его называют. Каждый коллега привязывает свой клон командой `trove clone <адрес-хранилища>`. Команда, которой нужна привязка в репозитории, использует `--share`: он пишет `.trove.yaml` для простого `trove clone`. Ассистенты живут по тому же правилу: `trove client add claude --local` держит их настройку на этой машине, и `trove init --client` делает так же, если хранилище не общее.

**Архив.** Рядом с рабочими папками лежит папка архива (по умолчанию `.archive/`), повторяющая их структуру.

**Тип документа.** Тип — набор возможностей, а не зашитое поведение:

| возможность | значит |
| ----------- | ------ |
| `ledger` | несёт таблицы открытых пунктов `<!-- ledger -->` — в колонках хранилища или в собственном `ledger:` типа |
| `status-line` | повторяет статус и дату сверки в видимой строке `**Статус документа:**` |
| `freshness` | устаревает, когда `checked` старше предела |
| `prompt-body` | текст задания начинается после `<!-- prompt -->` |
| `generated` | собирается `trove report`, руками не правится |
| `series`, `versions` | нумерация (`_2`) и версии (`_V2`); используются при создании документов |
| `resolved-of` | хранит закрытые пункты документа из `base`: реестр с теми же колонками и их разделы; `trove item close` переносит их сюда |
| `stages` | его этапы — то, что встретится первым вне сгенерированных блоков и кода: список задач (`- [x] …`, вложенные пункты не считаются), таблица с колонкой статуса или два и больше соседних заголовка либо жирных метки абзацев, которые начинаются с кодов этапов одного вида (`### Э1. Каталог`, `**Этап 2.** …`). Этап с кодом сделан, если у него есть отметка `[x]` или `✅`, значение «сделано» в скобках в конце (`(влит)`) или строка статуса сразу под ним (`**Статус:** влит`). Из названий убирается разметка, остаётся первое предложение, не длиннее примерно 80 символов. Читаются как поля `progress` (`3/5`), `next` (первый невыполненный этап) и `bar` (`3/5 ▰▰▰▱▱`); у документа в архиве или со статусом, с которым лежат в архиве, этапов нет |

**Что куда класть.** У каждого типа есть `purpose`: что в него входит и что нет. `trove regulation placement` печатает их одной таблицей, а AGENTS.md хранилища может встроить её между `<!-- regulation:placement -->` и `<!-- /regulation:placement -->`; каждый запуск отчётов её пересобирает, и заметки не расходятся с конфигом.

**Реестр.** Markdown-таблицы внутри блоков реестра; в документе их может быть несколько, и каждый пункт знает заголовок, под которым стоит (`section`). Колонки сопоставляются по подписи в шапке, поэтому таблицы с необязательными колонками и без них живут рядом. Тип со своим `ledger:` (id, колонки, статусы) держит его отдельно от аудитов, как это делают реестры долга или рисков. С `id: "DEBT-{section}{n}"` и `sections: { Server: S, Mobile: M }` каждая таблица нумерует свои id (`DEBT-S3`), а `trove item add DEBT section=Server …` добавляет пункт в эту таблицу и ставит его раздел после последнего раздела этой таблицы. `closed: { fixed: исправлено, dropped: снято }` перечисляет исходы закрытия, первый — по умолчанию; `note: "{status} {date}, {commit}"` — пометка в заголовке закрытого пункта. `heading: "{id}. {what}"` и `stub:` (строки Markdown с теми же подстановками) задают раздел, который пишет `item add`; пометка в скобках, которую писал не trove, остаётся частью названия.

**Закрытые пункты.** Тип с `closeInto: resolved` держит реестр только для открытой работы. `item close` переносит строку в реестр закрытых пунктов документа-спутника — `AUDIT_WEB_1.RESOLVED.md` рядом (те же колонки, в статусе — исход), а раздел пункта — под него, с пометкой в заголовке. Спутник создаётся при первом закрытии с `base:` и обратной ссылкой, хранит и рабочие материалы аудита и уезжает в архив вместе с аудитом.

**Сгенерированные блоки.** Любой документ, написанный руками, может содержать блок, который trove держит актуальным:

```md
<!-- trove:items owner=backend status=open group=section columns=id,what -->
<!-- /trove:items -->
```

Виды — `items`, `documents`, `progress` (документы с этапами, кроме завершённых: `3/5 ▰▰▰▱▱` и следующий этап, например `<!-- trove:progress type=plan place=work -->`), `counts` (`by=priority`), `placement`, `branches`, `changes` и `trend`; раскладку задают `as=table|list|ids`, `columns` (`document:аудит` переименовывает колонку), `label` (первая колонка `counts`), `group`, `sort` и `format="{id} — {what}"`, все остальные параметры — фильтры. Поле шапки `filter:` добавляется ко всем блокам документа. Каждая правка и каждый запуск отчётов перезаполняют блоки; документы в архиве сохраняют свои как снимок, как и сводка после своей даты `date`: это взгляд на тот день, а новый — `trove summary new`. Конфликт rebase внутри блока разрешается сам.

Три вида читают git — один раз за запуск и только если блок есть в документе. `branches` перечисляет ветки репозитория кода, подходящие под `pattern`, каждую один раз, новые сверху: свои коммиты ветки (которых нет ни в одной базе), сколько коммитов нет в каждой базе и дата последнего коммита: `<!-- trove:branches root=app pattern=feature/* against=origin/develop,origin/main -->`. Ветка, которая есть и локально, и как remote-tracking, показывается remote-tracking ссылкой, если только в локальной нет коммитов, которых нет в удалённой: тогда показывается локальная с пометкой `local ahead N`, а если ушли вперёд обе — удалённая с пометкой `local diverged`. Ветки, влитые во все базы, не показываются; `merged=true` показывает только их, `merged=any` — все; `active=30d` (или `6w`, `3m`) скрывает ветки, чей последний коммит старше. Если корня на этой машине нет, блок остаётся как есть. `changes` перечисляет пункты, закрытые, добавленные и перенесённые с некоторой точки, по истории самого хранилища: `since=previous`, по умолчанию, — коммит, впервые добавивший предыдущую сводку того же вида (ту, которую эта сводка заменяет, даже того же дня, иначе последнюю с более ранней датой, но никогда не соседнюю сводку того же дня), или её дата, если она не закоммичена; работает и `since=<коммит>`, а `since=<дата>` — последний коммит основной линии до этого дня, никогда не более старый коммит ветки, влитой позже. Пункт, перенесённый в документ с другим именем или закрытый как `moved`, считается перенесённым: `from` — где он был, `document` — куда ушёл, `to` — его новый id, который тогда не числится добавленным. Раскладка как у `items`, с колонкой `change`, фильтры те же; `group=change` и `group=document` делят список, `as=counts` считает пункты по изменениям, а с `by=document` (или другим полем) даёт строку на документ и колонку на изменение. `trend` считает по неделям, сколько пунктов открыто, сколько закрыто и сколько открыто на конец недели, по истории реестров: `<!-- trove:trend weeks=8 by=owner -->`. Недели начинаются с понедельника, последняя — текущая, `weeks` по умолчанию 8; `by` даёт строку на неделю и значение поля, фильтры пунктов работают. Неизвестный корень, база, срок или точка отсчёта — ошибка `live-block`. Подписи этих видов (`branch`, `ownCommits`, `localAhead`, `changeClosed`, `week`, `trendOpened`, …) берутся на языке хранилища `language`, если `labels` их не задают.

**Повторяемые проверки.** `verify:` словами говорит, как перепроверить документ; `verify-cmd:` говорит то же командой оболочки, например `verify-cmd: git -C "{root:app}" grep -q presence.v2 -- api/presence/hub.go`. Код выхода 0 значит, что сказанное в документе всё ещё верно: изменение из плана всё ещё в коде, спецификация всё ещё ему соответствует, находка аудита всё ещё на месте. Любой другой код значит, что документ устарел: перепроверьте его и поправьте документ или команду. `{root:<name>}` — абсолютный путь к этому корню кода, `{store}` — к хранилищу, оба с прямыми слешами; берите их в кавычки, если в пути могут быть пробелы.

Обычный `trove check` ничего не запускает. `trove check --verify` запускает команды документов в работе, не больше четырёх одновременно (`--jobs N`), каждую останавливает через 60 секунд (`--timeout SECONDS`); печатает по строке на документ, у не прошедшей команды — с концом её вывода, и выходит с кодом 1, если какая-то не прошла или не уложилась во время. Документ, чей корень не выложен на этой машине, пропускается. Команды выполняются в папке хранилища через оболочку Bun, одинаково на Windows, macOS и Linux (`&&`, `|`, `$VAR`, `cd`, `echo` и `exit` встроены; `test` или `grep` должны быть установлены, поэтому переносимый выбор — `git grep`), с закрытым stdin и без переменных git-хуков. Последний результат каждого документа хранится в `.trove/cache/verify.json`, а колонка `verified` в блоках `documents` и в `trove query documents` показывает его — `ok 2026-10-16` или `failed 2026-10-16` — ничего не запуская; она пуста, если команда на этой машине не запускалась или с тех пор изменилась.

**`--verify` выполняет команды оболочки, записанные в документах хранилища, с вашими правами.** Проверяйте изменения `verify-cmd` как код и запускайте его только на хранилищах, авторам которых доверяете.

**Отчёт.** Запрос плюс раскладка. `BACKLOG.md` — открытые пункты по владельцам; индекс промптов — документы-промпты по пути.

## Конфиг

```yaml
regulation: 1
language: ru
statuses: { open: открыт, closed: закрыт, archived: архив }

folders:
  audits: { prefix: AUDIT_, types: [audit] }

types:
  audit:
    capabilities: [ledger, status-line, freshness]
    fields: { slug: required }
  backlog:
    capabilities: [generated, status-line]

ledger:
  id: "{slug}-{n}"
  columns:
    - { key: id, label: id, required: true }
    - { key: status, label: статус, required: true, enum: { open: открыто, deferred: отложено } }
    - { key: what, label: что осталось, required: true }

lifecycle:
  audit:
    - { when: no-open-items, place: archive }

rules:
  unknown-field: off
  folder-type: { level: error, since: 2026-09-01 }   # более старые документы не проверяются

reports:
  backlog:
    output: BACKLOG.md
    type: backlog
    status: open
    title: Бэклог
    scope: все аудиты
    note: Собран из реестров аудитов.
    sections:
      - { from: items, where: { status: open }, groupBy: owner, sort: [id], columns: [id, what, document] }
```

`trove init` пишет полный конфиг из [английского или русского пресета](src/core/presets). Схема — в [`src/core/config/schema.ts`](src/core/config/schema.ts); перекрёстные ссылки, например папка с неизвестным типом, проверяются до чтения документов. `ignore` принимает имена файлов (`CONTRIBUTING.md`) и glob путей (`notes/**`); `archive.finished` перечисляет статусы, кроме `archived`, с которыми документ может лежать в архиве, например `done` или `dropped`. `stages: { status: [status, статус], done: [done, merged, готово] }` называет колонку статуса в таблице этапов и значения, которые значат, что этап сделан (после значения может идти продолжение, как в `влит 2026-10-01`); по умолчанию это распространённые английские и русские слова (`done`, `merged`, `shipped`, `released`, `готово`, `влито`, `в master` и другие) и `✓`, а `not done` или `не влито` сделанным не считается. `initial` типа задаёт статус новых документов, а `templates: <папка>` с `<type>.md` внутри заменяет встроенный шаблон (`{{name}}`, `{{title}}`, `{{status}}`, `{{date}}` и любые поля шапки; не заданное поле остаётся пустым, а заполнитель, который не является полем, отклоняется).

### Сводки

Сводка — датированный документ типа `summary`: сгенерированные блоки показывают состояние, написанные абзацы — анализ. Вид сводки задаёт заголовок, базовый фильтр и шаблон; `trove summary new weekly` создаёт `summaries/SUMMARY_WEEKLY_<дата>.md` с заполненными блоками и местами `<!-- write: … -->` для остального — правило `write-place` напоминает о них, пока под ними нет текста; сама строка остаётся, по ней следующая сводка находит место. Прежняя сводка этого вида уезжает в архив; `--from latest` переносит её написанный анализ по местам, чтобы править его, а не писать с нуля; новые блоки шаблона приходят без текста.

```yaml
summaries:
  web:
    title: Веб-клиент — что осталось
    filter: { path: "!audits/mobile/**" }  # добавляется к каждому блоку
    template: .trove/templates/web.md      # без него — встроенная раскладка
```

Шаблон — тело после строки статуса: Markdown, сгенерированные блоки и места для текста; `{{title}}`, `{{date}}` и `{{kind}}` подставляются. `<!-- trove:changes -->` в нём показывает, что закрыто, добавлено и перенесено с предыдущей сводки того же вида.

## Правила

| правило | по умолчанию | проверяет |
| ------- | ------------ | --------- |
| `front-matter` | error | документ начинается с блока `---` |
| `required-field` | error | обязательные поля типа на месте |
| `field-format` | error | поля-даты содержат настоящий `YYYY-MM-DD` |
| `unknown-field` | warn | встречаются только объявленные поля |
| `known-type` | error | тип объявлен |
| `known-status` | error | статус объявлен |
| `type-status` | error | статус разрешён для типа |
| `archive-status` | error | архивный статус тогда и только тогда, когда файл в папке архива; статус, с которым `lifecycle` отправляет в архив, или из `archive.finished`, там тоже считается архивным |
| `lifecycle` | error | документ лежит там, где велит `lifecycle` |
| `status-line` | error | строка статуса совпадает с шапкой |
| `ledger-block` | error | у типов с реестром есть закрытый блок реестра |
| `ledger-columns` | error | шапки реестра используют известные колонки и содержат обязательные |
| `ledger-row-shape` | error | в каждой строке столько ячеек, сколько в шапке |
| `id-hyphen` | error | в id ASCII-дефис, а не U+2011 |
| `id-format` | error | id следуют `ledger.id` |
| `item-enum` | error | ячейки со словарём содержат одно из его значений |
| `duplicate-id` | error | id уникальны во всём хранилище |
| `wait-refs` | warn | `blocked_by` и `until` называют существующие пункты, документы или закрытые пункты |
| `deferral-lifted` | warn | отсрочка, чей `until` уже выполнен |
| `item-size` | off | раздел пункта не больше `limit` байт, по умолчанию 2048: `item-size: { level: warn, limit: 2048, since: 2026-10-15 }` |
| `prompt-body` | error | у промптов есть маркер `<!-- prompt -->` |
| `header-refs` | error | поля `refs` называют существующие документы |
| `folder-type` | warn | документы соответствуют типам и префиксам своей папки |
| `dead-link` | warn | относительные ссылки ведут на файл в хранилище или в корне кода, который есть на этой машине |
| `live-block` | error | сгенерированные блоки `<!-- trove:… -->` закрыты и называют известный вид с допустимыми параметрами |
| `live-block-stale` | warn | сгенерированные блоки соответствуют хранилищу; правки внутри них затрёт следующий отчёт |
| `write-place` | warn | места для анализа, `<!-- write: … -->`, написаны |
| `stale` | info | рабочие документы сверяются в пределах срока свежести |

Любое правило можно выключить (`off`) или поменять ему уровень, `since` применяет его только к документам с датой не раньше указанной, а `limit` задаёт порог для правил, которые что-то измеряют.

### Свои правила

Положите скрипты в папку, указанную в `plugins:` конфига. Каждый экспортирует `rules`:

```ts
import { defineRule } from "trove";

export const rules = [
  defineRule({
    id: "no-todo",
    level: "warn",
    summary: "No TODO left in documents.",
    scope: "document",
    check: (doc) => (doc.text.includes("TODO") ? [{ message: "TODO left" }] : []),
  }),
];
```

## Библиотека

CLI — тонкий слой над ядром. Всё, что он делает, доступно как библиотека:

```ts
import { openStore, runRules, selectItems } from "trove";

const store = await openStore({ cwd: process.cwd() });
const errors = runRules(store.rules, store.index).filter((d) => d.severity === "error");
const urgent = selectItems(store.index, { priority: ["P0"], status: ["open"] });
```

## Разработка

```sh
bun install          # заодно ставит хук lefthook перед коммитом
bun run verify       # biome + bun check (TypeScript 7) + bun test
bun run trove check --store sandbox
```

| путь | что там |
| ---- | ------- |
| [`sandbox/`](sandbox) | Зелёное демо-хранилище выдуманного чат-приложения: аудиты с реестрами и приложениями, спеки, планы, исследования, study, инцидент, промпты, две сводки, архив. На нём удобно пробовать команды; CI проверяет его и актуальность его отчётов. |
| [`test/fixtures/broken/`](test/fixtures/broken) | Хранилище с одной подложенной ошибкой на правило, на русском пресете. |

Оба workflow запускаются и вручную: **Actions → ci → Run workflow** на любой ветке, при желании на одной ОС, и **release → Run workflow** на `main`; у упавшего запуска есть **Re-run failed jobs**.

`bun run e2e` прогоняет весь цикл через CLI во временной папке: `init`, `doc new`, `item add`, `item close --archive`, `check`, `doctor`.

**Релизы.** Каждое заметное для пользователя изменение добавляет заметку через `bunx changeset`. На `main` workflow релиза превращает накопленные заметки в PR `chore: release`; его слияние поднимает версию, пишет `CHANGELOG.md` и ставит тег. Если в репозитории Actions запрещено создавать PR, нужен секрет `GH_BYPASS_TOKEN` с правами на запись содержимого и pull request.

## План

- [x] **Ядро чтения.** Парсер, сохраняющий исходный текст, схема конфига, индекс, правила, отчёты; `check`, `report`, `query`, `show`, `prompt`.
- [x] **Хранилища и правки.** `init`, `clone`, `migrate`, `store add`, реестр машины, приватный или общий указатель; правки `doc` и `item`, меняющие только свои строки.
- [x] **Синхронизация.** Коммит на операцию, отправка с rebase и пересборкой отчётов, `trove sync` для ручных правок, `trove remote add`.
- [x] **MCP.** Один stdio-сервер над теми же операциями, регламент из конфига, несколько хранилищ на проект.
- [x] **Клиенты.** Скиллы для агентов, плагин Claude Code с хуками, `client add` для Cursor и Codex, однофайловые бинарники в каждом релизе.
- [x] **Миграция.** Архивы со своими статусами, колонками реестра и порядками подгоняет `migrate`, а `resync` держит их в согласии, пока идёт переезд.
