# trove

**Архив аудитов, планов и спецификаций в обычном Markdown — с одной проверкой.**

Правила живут в конфиге, а не в прозе. Markdown остаётся источником правды: люди читают файлы как есть, а инструмент их проверяет, ищет по ним и собирает отчёты.

```console
$ trove check
audits/AUDIT_WEB_1.md
  12  error  status line says closed, header open                 status-line
  21  error  7 cells against 6 in the header; a | inside a cell?  ledger-row-shape

✖ 2 errors, 0 warnings, 1 info · 20 documents · 5 ledgers · 16 open items
```

## Зачем

- **Один регламент.** Типы документов, статусы, колонки реестра и жизненный цикл — данные в `trove.yaml`. Новый тип, колонка или отчёт — правка конфига, а не кода.
- **Правда — в файлах.** Каждый документ — обычный Markdown в git. Всё, что хранит инструмент (индекс, сгенерированные отчёты), пересобирается из файлов.
- **Срезы, а не файлы.** `query` и `show` возвращают один пункт или один раздел: ни человеку, ни ассистенту не нужно открывать бэклог на 200 КБ ради одной находки.

## Быстрый старт

Нужен git. Возьмите однофайловый бинарник из [Releases](https://github.com/MkSavin/trove/releases) и положите в `PATH` как `trove` или установите из исходников через [Bun](https://bun.sh) ≥ 1.4.

```sh
bun add -g github:MkSavin/trove    # или бинарник из Releases
cd ~/git/app                       # ваш проект
trove init --lang ru               # ../app-trove: зелёное хранилище, связанное и закоммиченное
trove doc new audit "веб-клиент" --scope web/
trove item add AUDIT_WEB_CLIENT_1 priority=P1 owner=web "what=Отправка без сети теряется"
trove item close WEBCLIENT1-1 --commit 3f2a9c1
```

Коллега клонирует проект и запускает `trove clone`: каждое хранилище из `.trove.yaml` клонируется рядом и регистрируется. Уже ведёте такой архив руками? `trove migrate ../notes ../app-trove` соберёт из него хранилище: история git и незакоммиченная работа переедут, конфиг подгоняется под документы, а сам архив только читается.

## Команды

**Настройка**

| команда | что делает |
| ------- | ---------- |
| `trove init [--path] [--remote] [--lang en\|ru] [--no-git]` | Создаёт хранилище для текущего проекта: папки, конфиг, заметки, отчёты, git с проверкой перед коммитом, `.trove.yaml` в проекте, запись в `~/.trove/registry.yaml`. Задаёт не больше трёх вопросов, у каждого есть ответ по умолчанию; `--yes` принимает их все. |
| `trove clone` | Клонирует и регистрирует хранилища из `.trove.yaml` проекта. |
| `trove resync [--continue] [--seal]` | Переносит то, что изменилось в исходном архиве после миграции или прошлого `resync`, закоммиченное и нет, трёхсторонним слиянием: правки самого хранилища остаются, документ, который хранилище уже убрало в архив, получает изменение там, документ, который исходный архив перенёс в свою папку архива, переносится и в хранилище, конфликты ждут `--continue`. Исходный архив только читается, кроме `--seal`. |
| `trove migrate <archive> <store> [--drop FILE] [--project DIR [--link]]` | Собирает хранилище из существующего архива: клон с историей, незакоммиченная работа отдельным коммитом, конфиг под документы (язык, лишние типы, статусы и пишутся ли они ключами, поля, колонки реестра по типам, строка статуса только там, где она есть в документах, какие статусы лежат в архиве, порядок групп старого бэклога), пересобранные отчёты, подсчёт документов и пунктов до и после. Исходный архив только читается, его remote не переносится. |
| `trove store add <name> --scope <glob>` | Ещё одно хранилище — для команды со своим доступом; команды из папок под `--scope` идут в него. |
| `trove remote add <url>` | Подключает локальное хранилище к удалённому репозиторию, переключает `sync` на `push` и отправляет историю. |
| `trove client add <claude\|cursor\|codex>` | Регистрирует MCP-сервер и скиллы для ассистента в этом проекте. |
| `trove doctor` · `trove forget` | Показывает проект, его хранилища и их состояние · убирает проект из реестра этой машины. |

**Чтение**

| команда | что делает |
| ------- | ---------- |
| `trove check [file] [--all] [--json]` | Запускает все правила; при ошибках выходит с кодом 1. `--all` дополнительно перечисляет все документы. |
| `trove query items status=open owner=web` | Фильтрует пункты или документы по любому полю (см. фильтры ниже). |
| `trove summary show [kind] [filters]` | Сводка на экран, без записи: настроенный вид или подсчёты, открытые пункты по документам и документы в работе под заданными фильтрами. |
| `trove show WEB1-4` | Печатает раздел одного пункта. Принимает и `DOC#заголовок` или имя документа — тогда его оглавление. |
| `trove prompt PROMPT_X [--copy]` | Печатает текст задания промпта или копирует его; кириллица не ломается и в Windows. |
| `trove report [name...]` · `trove rules` | Пересобирает сгенерированные документы · список правил с действующим уровнем. |
| `trove links [--dead]` | Относительные ссылки на документы и код; код проверяется в `roots`, которые есть на этой машине: в рабочей копии или, с `{ path, ref: origin/main }`, на этом коммите, какая бы ветка ни была открыта. |
| `trove export items [filters] --format csv\|json` | Строки для CRM или таблицы; CSV по RFC 4180. |

**Правка.** Каждая правка меняет только свои строки, сохраняет CRLF, сначала проверяется в памяти и не записывается, если добавляет ошибку. Сгенерированные отчёты пересобираются тем же шагом; `--dry-run` вместо записи печатает построчный diff.

| команда | что делает |
| ------- | ---------- |
| `trove doc new <type> <topic> [--scope] [--field k=v]` | Документ по шаблону типа: папка, префикс, следующий номер серии, slug. |
| `trove doc archive <doc>` | Переносит в зеркальную папку архива, ставит статус, чинит относительные ссылки с обеих сторон. |
| `trove doc retype <doc> <type>` | Превращает документ в другой тип, например исследование, ставшее планом работ: папка, префикс, статус, заголовок, ссылки и упоминания следуют за ним. |
| `trove summary new <kind> [filters] [--name]` | Датированная сводка этого вида: сгенерированные блоки заполнены, места `<!-- write: … -->` оставлены для анализа. |
| `trove doc checked <doc>` · `trove doc set <doc> <field> <value>` | Сверено сегодня · любое поле шапки; `status` заодно обновляет строку статуса. |
| `trove item add <doc> column=value...` | Строка реестра со следующим свободным id и заготовкой раздела. Номера закрытых пунктов не переиспользуются. |
| `trove item close <id> [--commit SHA] [--archive]` | Убирает строку, помечает раздел закрытым, перечисляет другие упоминания; `--archive` — если это был последний открытый пункт. |
| `trove item defer <id>` | Ячейку статуса и пометку раздела — в «отложено». |
| `trove item move <id> <doc> [--archive]` | Переносит пункт с разделом в другой реестр под следующим id там; колонки, которых нет у цели, перечисляются. |
| `trove sync [-m TEXT]` | Коммитит ручные правки вместе с пересобранными отчётами и отправляет по режиму. Не работает, пока `check` красный. |

**Фильтры** одинаковы в `query`, `summary`, `export`, конфигах отчётов, сгенерированных блоках и инструментах MCP: `field=value` совпадает с сырым текстом или ключом словаря (`status=open` и `status=открыто` — одно и то же), `~text` — подстрока, `*` и `**` — glob, `!` в начале исключает. Пункты фильтруются и по полям своего документа: `owner=web path=!audits/mobile/**` — всё для веб-команды вне мобильных аудитов. Повторите поле или перечислите через запятую, чтобы задать варианты.

Команды находят хранилище от текущей папки: внутри хранилища, затем через `.trove.yaml` проекта (по `scope`, если их несколько), затем через реестр. `--store <name|dir>` или `$TROVE_STORE` задают его явно.

**Синхронизация.** `sync:` в `trove.yaml` решает, что происходит после правки: `off` не трогает git, `commit` делает один коммит на операцию (`docs: close WEB1-3`), `push` ещё и отправляет. Если удалённая ветка ушла вперёд, trove делает rebase; конфликты в сгенерированных отчётах берут удалённую копию и пересобираются, конфликт в документе, написанном руками, останавливает работу с именем файла, ничего не отправив. Пока `check` красный, ничего не коммитится, force push не делается никогда, а хранилище внутри другого репозитория в него не коммитит.

**Переезд архива.** Хранилище после миграции продолжает git-историю архива, поэтому `migrate` не задаёт remote: отправка хранилища в `origin` архива превратила бы тот репозиторий в хранилище для всех, кто ещё пишет в архив по-старому. Вместо этого он печатает remote архива, готовую команду `trove remote add <url>` и сколько коммитов архива на этом remote ещё нет; дайте хранилищу собственный репозиторий или берите старый только после запечатывания. Пока в архиве ещё работают, `trove resync` держит хранилище в согласии с ним, а `trove doctor` предупреждает, если архив изменился после последнего `resync`. Когда переезд закончен, `trove resync --seal` переносит последние изменения, затем пишет в архив `MOVED.md`, ставит первой строкой его `AGENTS.md` (создав файл, если его нет), где теперь хранилище и что в архив писать нельзя, и коммитит оба файла там, если это git-репозиторий. Это единственная команда, которая пишет в архив.

## MCP

`trove mcp` отдаёт те же операции ассистенту по stdio — для хранилищ папки, в которой запущен. Двенадцать инструментов, каждый покрывает семейство операций через дискриминатор, поэтому список инструментов дёшев в любой сессии:

| инструмент | что делает |
| ---------- | ---------- |
| `trove_query` · `trove_show` | строки пунктов или документов по фильтрам · раздел одного пункта, `DOC#заголовок` или оглавление |
| `trove_summary` | сводка настроенного вида или собранная по фильтрам, без записи |
| `trove_check` · `trove_regulation` · `trove_prompt` | диагностика · как устроено это хранилище, по его конфигу · текст задания промпта |
| `trove_create` · `trove_update` · `trove_transition` | новый документ по шаблону · поле шапки · перенос в архив с починкой ссылок |
| `trove_item` | `add`, `close`, `defer`, `move` для пунктов реестра |
| `trove_report` · `trove_sync` | пересборка сгенерированных документов · коммит ручных правок и отправка |

Правки возвращают затронутые файлы с построчным diff; `dryRun: true` возвращает diff без записи, а отклонённая правка перечисляет ошибки, которые она добавила бы. Ресурсы: `trove://regulation/{topic}`, `trove://config`, `trove://template/{type}`.

### Ассистенты

| клиент | как подключить |
| ------ | -------------- |
| Claude Code | `/plugin marketplace add MkSavin/trove`, затем `/plugin install trove@trove-marketplace`: MCP-сервер, оба скилла и хуки, которые запускают `check` на каждом изменённом документе хранилища и `sync` в конце сессии. |
| Cursor | `trove client add cursor`: `.cursor/mcp.json` и `.cursor/skills/`. |
| Codex | `trove client add codex`: `[mcp_servers.trove]` в `.codex/config.toml` и `.agents/skills/`. |
| любой | `trove client add claude` пишет `.mcp.json` и `.claude/skills/` без плагина; `trove init --client <name>` делает это при создании. |

Скиллы `trove-store` и `trove-migrate` лежат в одном месте, [`plugin/skills`](plugin/skills), и встраиваются в бинарник, поэтому все клиенты получают один и тот же текст.

## Понятия

**Проект и хранилище.** Проект — ваш репозиторий с кодом. Хранилище — отдельный git-репозиторий его документов, по умолчанию рядом. В проекте лежит один файл-указатель, `.trove.yaml`; на машине — `~/.trove/registry.yaml`. Доступ к хранилищу — это доступ к его репозиторию.

**Архив.** Рядом с рабочими папками лежит папка архива (по умолчанию `.archive/`), повторяющая их структуру.

**Тип документа.** Тип — набор возможностей, а не зашитое поведение:

| возможность | значит |
| ----------- | ------ |
| `ledger` | несёт таблицы открытых пунктов `<!-- ledger -->` — в колонках хранилища или в собственном `ledger:` типа |
| `status-line` | повторяет статус и дату сверки в видимой строке `**Статус документа:**` |
| `freshness` | устаревает, когда `checked` старше предела |
| `prompt-body` | текст задания начинается после `<!-- prompt -->` |
| `generated` | собирается `trove report`, руками не правится |
| `series`, `versions`, `addition-of` | нумерация (`_2`), версии (`_V2`) и приложения; используются при создании документов |

**Что куда класть.** У каждого типа есть `purpose`: что в него входит и что нет. `trove regulation placement` печатает их одной таблицей, а AGENTS.md хранилища может встроить её между `<!-- regulation:placement -->` и `<!-- /regulation:placement -->`; каждый запуск отчётов её пересобирает, и заметки не расходятся с конфигом.

**Реестр.** Markdown-таблицы внутри блоков реестра; в документе их может быть несколько, и каждый пункт знает заголовок, под которым стоит (`section`). Колонки сопоставляются по подписи в шапке, поэтому таблицы с необязательными колонками и без них живут рядом. Тип со своим `ledger:` (id, колонки, статусы) держит его отдельно от аудитов, как это делают реестры долга или рисков. С `id: "DEBT-{section}{n}"` и `sections: { Server: S, Mobile: M }` каждая таблица нумерует свои id (`DEBT-S3`), а `trove item add DEBT section=Server …` добавляет пункт в эту таблицу и ставит его раздел после последнего раздела этой таблицы. `closed: "закрыто {date}, {commit}"` задаёт пометку в заголовке закрытого пункта.

**Сгенерированные блоки.** Любой документ, написанный руками, может содержать блок, который trove держит актуальным:

```md
<!-- trove:items owner=backend status=open group=section columns=id,what -->
<!-- /trove:items -->
```

Виды — `items`, `documents`, `counts` (`by=priority`) и `placement`; раскладку задают `as=table|list|ids`, `columns` (`document:аудит` переименовывает колонку), `label` (первая колонка `counts`), `group`, `sort` и `format="{id} — {what}"`, все остальные параметры — фильтры. Поле шапки `filter:` добавляется ко всем блокам документа. Каждая правка и каждый запуск отчётов перезаполняют блоки; документы в архиве сохраняют свои как снимок, а конфликт rebase внутри блока разрешается сам.

**Отчёт.** Запрос плюс раскладка. `BACKLOG.md` — открытые пункты по владельцам; индекс промптов — документы-промпты по пути.

## Конфиг

```yaml
regulation: 1
language: ru
statuses: { open: открыт, closed: закрыт, archived: архив }

folders:
  audits: { prefix: AUDIT_, types: [audit] }

types:
  audit:
    capabilities: [ledger, status-line, freshness]
    fields: { slug: required }
  backlog:
    capabilities: [generated, status-line]

ledger:
  id: "{slug}-{n}"
  columns:
    - { key: id, label: id, required: true }
    - { key: status, label: статус, required: true, enum: { open: открыто, deferred: отложено } }
    - { key: what, label: что осталось, required: true }

lifecycle:
  audit:
    - { when: no-open-items, place: archive }

rules:
  unknown-field: off
  folder-type: { level: error, since: 2026-09-01 }   # более старые документы не проверяются

reports:
  backlog:
    output: BACKLOG.md
    type: backlog
    status: open
    title: Бэклог
    scope: все аудиты
    note: Собран из реестров аудитов.
    sections:
      - { from: items, where: { status: open }, groupBy: owner, sort: [id], columns: [id, what, document] }
```

`trove init` пишет полный конфиг из [английского или русского пресета](src/core/presets). Схема — в [`src/core/config/schema.ts`](src/core/config/schema.ts); перекрёстные ссылки, например папка с неизвестным типом, проверяются до чтения документов. `ignore` принимает имена файлов (`CONTRIBUTING.md`) и glob путей (`notes/**`); `archive.finished` перечисляет статусы, кроме `archived`, с которыми документ может лежать в архиве, например `done` или `dropped`. `initial` типа задаёт статус новых документов, а `templates: <папка>` с `<type>.md` внутри заменяет встроенный шаблон (`{{name}}`, `{{title}}`, `{{status}}`, `{{date}}` и любые поля шапки).

### Сводки

Сводка — датированный документ типа `summary`: сгенерированные блоки показывают состояние, написанные абзацы — анализ. Вид сводки задаёт заголовок, базовый фильтр и шаблон; `trove summary new weekly` создаёт `summaries/SUMMARY_WEEKLY_<дата>.md` с заполненными блоками и местами `<!-- write: … -->` для остального — правило `write-place` напоминает о них, пока они не написаны.

```yaml
summaries:
  web:
    title: Веб-клиент — что осталось
    filter: { path: "!audits/mobile/**" }  # добавляется к каждому блоку
    template: .trove/templates/web.md      # без него — встроенная раскладка
```

Шаблон — тело после строки статуса: Markdown, сгенерированные блоки и места для текста; `{{title}}`, `{{date}}` и `{{kind}}` подставляются.

## Правила

| правило | по умолчанию | проверяет |
| ------- | ------------ | --------- |
| `front-matter` | error | документ начинается с блока `---` |
| `required-field` | error | обязательные поля типа на месте |
| `field-format` | error | поля-даты содержат настоящий `YYYY-MM-DD` |
| `unknown-field` | warn | встречаются только объявленные поля |
| `known-type` | error | тип объявлен |
| `known-status` | error | статус объявлен |
| `type-status` | error | статус разрешён для типа |
| `archive-status` | error | архивный статус тогда и только тогда, когда файл в папке архива |
| `lifecycle` | error | документ лежит там, где велит `lifecycle` |
| `status-line` | error | строка статуса совпадает с шапкой |
| `ledger-block` | error | у типов с реестром есть закрытый блок реестра |
| `ledger-columns` | error | шапки реестра используют известные колонки и содержат обязательные |
| `ledger-row-shape` | error | в каждой строке столько ячеек, сколько в шапке |
| `id-hyphen` | error | в id ASCII-дефис, а не U+2011 |
| `id-format` | error | id следуют `ledger.id` |
| `item-enum` | error | ячейки со словарём содержат одно из его значений |
| `duplicate-id` | error | id уникальны во всём хранилище |
| `prompt-body` | error | у промптов есть маркер `<!-- prompt -->` |
| `header-refs` | error | поля `refs` называют существующие документы |
| `folder-type` | warn | документы соответствуют типам и префиксам своей папки |
| `dead-link` | warn | относительные ссылки ведут на файл в хранилище или в корне кода, который есть на этой машине |
| `live-block` | error | сгенерированные блоки `<!-- trove:… -->` закрыты и называют известный вид с допустимыми параметрами |
| `live-block-stale` | warn | сгенерированные блоки соответствуют хранилищу; правки внутри них затрёт следующий отчёт |
| `write-place` | warn | места для анализа, `<!-- write: … -->`, написаны |
| `stale` | info | рабочие документы сверяются в пределах срока свежести |

Любое правило можно выключить (`off`) или поменять ему уровень, а `since` применяет его только к документам с датой не раньше указанной.

### Свои правила

Положите скрипты в папку, указанную в `plugins:` конфига. Каждый экспортирует `rules`:

```ts
import { defineRule } from "trove";

export const rules = [
  defineRule({
    id: "no-todo",
    level: "warn",
    summary: "No TODO left in documents.",
    scope: "document",
    check: (doc) => (doc.text.includes("TODO") ? [{ message: "TODO left" }] : []),
  }),
];
```

## Библиотека

CLI — тонкий слой над ядром. Всё, что он делает, доступно как библиотека:

```ts
import { openStore, runRules, selectItems } from "trove";

const store = await openStore({ cwd: process.cwd() });
const errors = runRules(store.rules, store.index).filter((d) => d.severity === "error");
const urgent = selectItems(store.index, { priority: ["P0"], status: ["open"] });
```

## Разработка

```sh
bun install          # заодно ставит хук lefthook перед коммитом
bun run verify       # biome + bun check (TypeScript 7) + bun test
bun run trove check --store sandbox
```

| путь | что там |
| ---- | ------- |
| [`sandbox/`](sandbox) | Зелёное демо-хранилище выдуманного чат-приложения: аудиты с реестрами и приложениями, спеки, планы, исследования, study, инцидент, промпты, две сводки, архив. На нём удобно пробовать команды; CI проверяет его и актуальность его отчётов. |
| [`test/fixtures/broken/`](test/fixtures/broken) | Хранилище с одной подложенной ошибкой на правило, на русском пресете. |

Оба workflow запускаются и вручную: **Actions → ci → Run workflow** на любой ветке, при желании на одной ОС, и **release → Run workflow** на `main`; у упавшего запуска есть **Re-run failed jobs**.

`bun run e2e` прогоняет весь цикл через CLI во временной папке: `init`, `doc new`, `item add`, `item close --archive`, `check`, `doctor`.

**Релизы.** Каждое заметное для пользователя изменение добавляет заметку через `bunx changeset`. На `main` workflow релиза превращает накопленные заметки в PR `chore: release`; его слияние поднимает версию, пишет `CHANGELOG.md` и ставит тег. Если в репозитории Actions запрещено создавать PR, нужен секрет `GH_BYPASS_TOKEN` с правами на запись содержимого и pull request.
